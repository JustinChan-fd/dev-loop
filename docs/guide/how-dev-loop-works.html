How dev-loop works

dev-loop is a Node.js program that runs on your Mac and turns a Jira ticket into a tested, signed pull request. It isn't a skill itself: it wraps the robot's skills (research, then build), starts each one, and does the routine steps around them.

Key pillars

The six rules every part of dev-loop follows.

  1. The robot thinks, the loop does the routine. The robot (its skills) reads, plans and writes code. dev-loop's own code does the fixed steps: Jira, GitHub, signing, cleanup.
  2. Tests first, always. Every requirement gets a failing test before any code is written.
  3. A bounce beats a guess. If something is unclear or won't work, the robot stops and says why instead of guessing.
  4. Your key stays with you. Only your Mac signs and sends. The robot never holds your key.
  5. Locked down when you want it. With a safety room, the robot reaches only approved services.
  6. We follow our own rules. dev-loop is built the same way it builds your repos: long unattended work runs in a safety room, your Mac signs and sends, and every change reaches main through a PR you approve.

      Repos we support

      Adding a repo needs no code. Copy one of the pipeline.<repo>.config.json files at the root of dev-loop, fill in the new repo's GitHub name, Jira labels and statuses, then run npm run loop -- --project=<repo>. If the code lives in a folder like app/ or pins its Node, add a local block. Steps are in docs/config.md; each repo's layout and quirks are in docs/projects/.

      05

      How we build dev-loop

      The same rules, on dev-loop's own code. Two ways to start Claude on it; which one is your call each session, and long unattended work is offered the sandbox first.

      claude --dangerously-skip-permissions # normal session, unchanged
      npm run claude:sbx # same, but inside the sandbox

      Details, including the overnight mode and how the work comes back: docs/sandbox-sbx.md, "Dev-loop sessions".
