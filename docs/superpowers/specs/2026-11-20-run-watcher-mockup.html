Run watcher: one page, three views

This is one dashboard with a view switch. Runs combines the feed, step tracks and corner glance. Timeline lays runs out by time, one lane per worker. Batch shows a stack of tickets and what each one is waiting on.

Use the scenario switch to compare today (one worker, one ticket at a time) with a possible future batch (3 workers building a stacked set of tickets). Drag the frame's bottom-right corner to resize it (Narrow, about 480px, is the smallest it's designed for). The demo data moves every few seconds.

How the four ideas combined

  • Runs is the feed (A) as full-width cards, with the corner counts (D) on top. Every card, live or finished, carries the labeled step bar (B).
  • The step bar says where a run ended. Done steps have a check. The step it ended on is filled in the outcome's color with its mark: ✕ error, ↩ bounced, ■ stopped, Ⅱ parked. Steps it never reached are dashed.
  • Timeline has a direction switch so the three candidates can be compared: by run (the original C), by worker, and an activity stream. The plan is to keep one.
  • Batch is new. It only matters once batch mode exists, so with no batch running it shows what it would display.
  • Clicking a card opens its full log, grouped by step, with how long each step took and every line in full. Steps it never reached are listed at the end.
  • Links: the ticket key opens Jira, #N opens the ticket's GitHub issue, PR N opens the pull request once one exists. Each opens in a new tab and doesn't expand the row.

Filters

  • Project, phase, worker are dropdowns that apply to every view. "Agent" here is split into phase (research or dev) and worker (dev-1, dev-2, ...), since those are what the files record.
  • Outcome: click a count on top (running, landed, bounced, failed) to show only those. Click it again to clear.
  • Group by project or worker turns the list into sections. Filters stay in the URL so a bookmarked view comes back the same.
  • Filtering by subagent (recon, devil's advocate, QA) is possible only if the skills name the subagent in their progress lines. Some already do; it isn't guaranteed.

What batch would need from the loop

  • Workers, runs and outcomes come from files that exist today. The batch view needs one more thing: a batch file listing its tickets, which ticket each one depends on, and its base branch.
  • That file would be written by the batch orchestrator (v2 design §8), not by the dashboard. The dashboard only reads.
  • Ticket states come from facts: waiting (dependency not done), running (a live lock), PR open, landed, blocked (its dependency bounced or errored).
